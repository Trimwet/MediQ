## 2. `supabase/migrations/*` — RLS for `rooms` / `staff` / `doctors`

**Per `src/config/rbac.ts:19-55`:** `front_desk` has `patients:view/manage` but **not** `staff:view/manage`, `doctors:view/manage`, `rooms:view/manage`. `doctor` has only `patients:view` / `appointments:view` / `queue:view`. Frontend route guard (`src/config/rbac.ts:64-72`) therefore **blocks** `/admin/staff`, `/admin/doctors`, `/admin/rooms` for `front_desk` and `doctor`. The earlier bug bounty hunting infra expected “front_desk can read but not write” — that expectation is **opposite** of `rbac.ts`. The canonical answer is: RLS is more permissive than RBAC on SELECT, which is acceptable (defense-in-depth), but WRITE must be admin-only. Final migrations do this correctly.

| # | File:Line | Severity | Finding |
|---|-----------|----------|---------|
| **RLS-01** | `supabase/migrations/*` vs `mediq-admin/supabase/migrations/*` | **Critical** | **Two canonical migration trees diverged.** `mediq-admin/supabase/migrations/` contains only `20260820_multi_tenancy.sql:1` + `20260825_notifications_audit_hardening.sql:1`. `supabase/migrations/` contains 18 incremental files (`20260819113813_init.sql:1`, `20260821000000_clinics.sql:1`, `20260821100000_fix_tenancy_bugs.sql:1`, `20260821200000_fix_tenancy_warnings.sql:1`, `20260829000000_fix_patient_queue_and_insert.sql:1`, etc.). Final effective policies differ between the two paths. Any `supabase db push` that applies one tree and not the other leaves RLS in a different state than the repo documents. **Fix:** delete `mediq-admin/supabase/migrations/` (it is a fork) and keep `supabase/migrations/` as single source of truth, or add CI check that both directories hash to same `pg_dump` output. |
| **RLS-02** | `supabase/migrations/20260819113813_init.sql:214-275` → `supabase/migrations/20260821000000_clinics.sql:1` → `supabase/migrations/20260821200000_fix_tenancy_warnings.sql:1` (W7) | **Important** | **Read vs write verdict — matches `rbac.ts` intent after W7.** `init` set `doctors_select_roles` / `staff_select_staff` / `rooms_select_roles` to `is_admin() OR has_role('front_desk') OR has_role('doctor')` → front_desk+doctor **can** read (more permissive than RBAC's `staff:view` gate, but acceptable as DB layer). Result: **front_desk and doctor can SELECT but cannot INSERT/UPDATE/DELETE** doctors/staff/rooms. Staff rows become immutable via RLS (updates silently affect 0 rows). W7 fork correctly adds `staff_update_clinic` with `USING/WITH CHECK (user_in_clinic AND (is_admin() OR user_is_clinic_admin))`. If hardening fork is deployed, staff edits (e.g., correcting phone, toggling `status`) fail with no error. |
| **RLS-05** | `supabase/migrations/20260821000000_clinics.sql:30-55` (`user_is_clinic_admin`) vs `supabase/migrations/20260821200000_fix_tenancy_warnings.sql:1` (W7) vs `mediq-admin/supabase/migrations/20260825_notifications_audit_hardening.sql:1` | **Important** | **`is_admin` vs `user_is_clinic_admin` correctness.** Early `clinics.sql` defines `user_is_clinic_admin(c_clinic_id)` as `exists select from clinic_members where role='admin'` **without platform fallback**. | **RLS-07** | `supabase/migrations/20260819113813_init.sql:185-210` (`doctors.status check`) | Info | No bug, but note: `doctors.specialization` CHECK enumerates 6 values; verify `General Practice` default in `invite-staff:73` is within that list (it is). No mismatch. |
